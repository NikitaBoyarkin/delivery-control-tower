# Синтетический стенд

Полноразмерный датасет-двойник для локального прогона пайплайна, когда исходных
CSV нет. Генерируется `scripts/make_dummy_dataset.py`.

> Это **не исходные данные** и не их побайтовая копия. Числа откалиброваны по
> опубликованным агрегатам, но каждая строка синтетическая. Ссылаться на этот
> файл как на источник данных задания нельзя.

## Зачем

`data/raw/city_day_channel_category.csv` и `data/raw/orders_sample.csv` не
публиковались (см. [data_sources.md](data_sources.md)), а `scripts/make_synthetic_data.py`
специально делает маленькую заглушку для CI: 60 городов, каналы `mp/web/app`,
категории `пицца/суши/бургеры/десерты`. Этого хватает тестам, но не хватает
пайплайну: витрины, прогноз, разбор узких мест и гипотезы на ней считаются, а
числа в README не воспроизводятся.

Синтетический стенд закрывает этот разрыв: схема та же, размер тот же, эффекты
те же — но данные сгенерированы, а не получены из задания.

## Что генерируется

| Файл | Строк | Колонки |
|---|---:|---|
| `city_day_channel_category.csv` | 550 710 | `Date, CityName, OrderSource, Category, rto, rto_do, cost, qty, tickets, clients_qty, avg_time, avg_price` |
| `orders_sample.csv` | 130 079 | `cityname, date, clientid, orderid, sales` |

Покрытие: 181 день (2022-01-01..2022-06-30), 264 города, 3 канала (`mp`, `web`,
`other`), 4 категории (`пицца`, `закуски`, `напитки`, `десерты`). Сетка неполная,
как в источнике: 550 710 из 573 408 возможных ячеек (96,0 %).

## Калибровка

Опубликованные значения взяты из README и `docs/data_dictionary.md`; фактические
— из прогона `--validate` на этом стенде.

Точные суммы (`qty`, `tickets`, `clients_qty`, `cost`, среднее `avg_price`)
достигаются целочисленным распределением остатка: сначала веса масштабируются в
непрерывные значения, затем округляются с сохранением суммы и границ
(`1 ≤ tickets ≤ qty`, `1 ≤ clients_qty ≤ tickets`). Поэтому контрольные суммы
совпадают до единицы, а не «примерно».

## Какие правила зашиты

- **Размер городов.** Лог-нормальное распределение плюс фиксированные доли
  Москвы (12,3 %) и Санкт-Петербурга (7,1 %).
- **Сезонность.** День недели (пятница и суббота — пик), месяц (май и июнь выше
  января), праздники: 23 февраля ×1,85, 9 мая ×1,75, 8 марта ×1,70, 1 июня
  ×1,60, плюс провалы 1 января и начала марта.
- **Микс каналов.** Доля `web` падает с 16,2 % до 10,1 %, доля `other` растёт с
  11,3 % до 18,3 %; за счёт этого доля `mp` в паре `mp+web` растёт на 5,4 п.п.
- **Категории.** Константы времени доставки: закуски 39,97 мин, напитки 30,01,
  пицца 26,55, десерты 24,99. Внутри категории — городской сдвиг и дневной шум;
  шум у напитков и пиццы шире, чем у закусок и десертов.
- **Объём и время.** Наклон −0,229 мин на логарифм объёма города даёт слабую
  отрицательную ранговую корреляцию (ρ ≈ −0,09): крупные города чуть быстрее,
  роста времени с нагрузкой нет.
- **Выходные.** Сдвиг −0,25 мин; вместе с более высоким объёмом это даёт
  −0,23 мин к будням — направление как в источнике (H2 отклонена).
- **Разреженность.** Пропуски чаще у малых городов и в каналах `web`/`other`,
  реже у `mp` и пиццы: 22 698 пропущенных ячеек.
- **Заказы.** Два города (`city1` 81,1 % заказов, `city2` 18,9 %), 31 426
  клиентов, тяжёлый хвост по числу заказов на клиента, чек из эмпирических
  квантилей источника (медиана 859, хвост до 16 098), 619 нулевых чеков.

## Как запустить

```bash
# полный стенд в data/synthetic/ + проверка контракта (etl → quality → marts)
uv run python scripts/make_dummy_dataset.py --validate

# то же плюс прогноз, узкие места, H1/H2 и дашборд
uv run python scripts/make_dummy_dataset.py --validate --full

# маленький вариант для быстрых проверок (40 городов, 3 000 заказов)
uv run python scripts/make_dummy_dataset.py --out /tmp/dct-small --scale 0.15 --validate

# другой сид — другой датасет с теми же контрактами
uv run python scripts/make_dummy_dataset.py --seed 7 --validate
```

Генератор детерминирован: один и тот же `--seed` даёт побайтово одинаковые CSV.

## Как прогнать на нём весь пайплайн

`delivery.etl` читает `data/raw/`, поэтому оригиналы надо временно убрать:

```bash
mv data/raw/city_day_channel_category.csv data/raw/city_day_channel_category.real.csv
mv data/raw/orders_sample.csv            data/raw/orders_sample.real.csv
cp data/synthetic/*.csv data/raw/

uv run python -m delivery.etl
uv run python -m delivery.marts
uv run python -m delivery.forecast
uv run python -m delivery.bottlenecks
uv run python -m delivery.hypothesis
uv run python scripts/ab_test_analyzer.py --readout all
uv run python -m delivery.sql_layer
uv run python -m delivery.dashboard

# вернуть оригиналы
mv data/raw/city_day_channel_category.real.csv data/raw/city_day_channel_category.csv
mv data/raw/orders_sample.real.csv            data/raw/orders_sample.csv
```

`--validate --full` делает то же самое во временном каталоге и не трогает
`data/raw/` — это безопасный способ проверить стенд.

## Чего стенд не воспроизводит

- **Города поимённо.** Имена настоящие, но объёмы и сдвиги времени у них
  синтетические. Рейтинг городов из README (Усолье-Сибирское, Грозный) на этом
  стенде не повторится — и не должен.
- **Связь заказов с агрегатом.** Выборка заказов живёт отдельно: её нельзя
  сложить с `fact_sales` и получить те же чеки.
- **Семантику `cost` и `avg_price`.** `cost` остаётся «в единицах источника»,
  валюты у него нет; `avg_price` выводится как `rto / qty`, как в источнике, но
  что именно он измеряет — по-прежнему не подтверждено.
- **Дефекты источника.** Отрицательных `avg_time`, нулевых `cost` и прочих
  аномалий здесь нет: стенд чище оригинала. Это осознанно.
- **Точные значения SQL-замеров.** Ускорения из README зависят от машины; стенд
  даёт те же по порядку величины, но не те же миллисекунды.

## Ограничения

Стенд не заменяет исходные CSV для аудита: он воспроизводит опубликованные
агрегаты, а не происхождение данных. Если задание опубликуют заново, оригиналы
надо положить в `data/raw/` и обновить контрольные суммы в
[data_sources.md](data_sources.md); синтетика останется только для локальных
прогонов и CI.
