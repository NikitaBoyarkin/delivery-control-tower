**Новая находка P0, найденная при верификации артефактов — `active_clients_30d` врёт 144 дня
из 181.** Оконная рамка задана как `RANGE BETWEEN 29 PRECEDING` по целочисленному
`date_key` (YYYYMMDD). Это арифметика по числу, а не по дате: для любого дня после 29-го
нижняя граница попадает в несуществующие ключи (`20220172 …`), и окно молча сжимается до
«дней с начала месяца». Пример: 2022-02-01 запрос даёт **529** активных клиентов против
**10 111** в настоящем календарном окне; максимальное расхождение — **10 748** клиентов.
Последний день (2022-06-30) верен, потому что июнь ровно 30 дней — поэтому «12 318 на
30.06» из README не пострадало. Исправлено: окно переведено на календарный `date` из
`dim_date` (`sql/windows.sql:118-141`), тест сверяет результат с независимым пересчётом
через `JOIN`+`COUNT(DISTINCT)` по календарю (`tests/test_sql_layer.py:89`), а не с
диапазоном `0 < value <= total`, который пропускал этот дефект.

Остальные находки ревью закрыты в том же заходе: `scripts/make_synthetic_data.py` больше
не может затереть боевые `data/raw/*.csv` (требует `--base`, отказывается перезаписывать

`pytest_sessionfinish` роняет зелёный прогон с любым числом скипов.
