# Delivery Control Tower — аналитический отчёт

## 1. Задача и данные

Задача — понять, где процесс доставки теряет время и можно ли прогнозировать
объём заказов достаточно точно, чтобы планировать под него загрузку.

Источник — агрегат из открытого тестового задания (Dodo Brands):
**день × город × канал × категория** за **2022-01-01 .. 2022-06-30**,
**550 710 строк**, **264 города**, **3 канала** (`mp`, `web`, `other`),
**4 категории** (пицца, закуски, напитки, десерты), 181 день. Второй файл —
сэмпл **130 079 заказов** по **2 анонимным городам**, он используется только
для SQL-слоя.

Семантика полей, принятая в работе:

| Поле | Что значит | Проверка |
|---|---|---|
| `tickets` | заказы (чеки), не обращения в поддержку | `SUM(tickets)` = 33 167 293; `SUM(qty)/SUM(tickets)` = 1.736 |
| `qty` | позиции (блюда) | `SUM(qty)` = 57 576 550 |
| `clients_qty` | уникальные клиенты внутри ячейки | `SUM(clients_qty)/SUM(tickets)` = 0.94 |
| `cost` | денежная метрика источника | `SUM(cost)/SUM(tickets)` = 138.9; **валюта не подтверждена** |
| `avg_price` | средняя цена из источника | не согласуется с `cost` (221.8 против 138.9) — **не используется** |
| `avg_time` | время доставки, минуты | при агрегации взвешивается по `qty` |

`cost` нигде не называется выручкой: это денежная метрика в неподтверждённых
единицах источника. Полный словарь — `docs/data_dictionary.md`.

## 2. Как устроен пайплайн

| Слой | Модуль | Что делает |
|---|---|---|
| Raw → staging | `delivery/etl.py` | копирует исходные CSV, нормализует типы, добавляет календарные колонки, пишет parquet |
| Контроль качества | `delivery/quality.py` | именованные проверки: число строк, уникальность гранулярности, диапазоны дат |
| Star schema | `delivery/marts.py` | `dim_date`, `dim_city`, `dim_channel`, `dim_category`, `dim_client`, `dim_order_city`, `fact_sales`, `fact_orders` и витрины `mart_daily_total`, `mart_city_daily`, `mart_delivery` в DuckDB |
| Прогноз | `delivery/forecast.py` | rolling-origin бэктест: тестовое окно 28 дней, 4 фолда, переобучение каждые 7 дней, горизонты 1/7/14 |
| Узкие места | `delivery/bottlenecks.py` | декомпозиция времени по каналу × категории, кривая нагрузки по децилям объёма, наклон деградации по городам |
| Гипотезы | `delivery/hypothesis.py` | Mann-Whitney U + bootstrap-интервал; гипотеза считается подтверждённой только если p < α **и** интервал не содержит ноль |
| SQL-слой | `delivery/sql_layer.py` | 14 именованных оконных запросов, 3 пары оптимизаций под `EXPLAIN ANALYZE` |
| Презентация | `delivery/dashboard.py` | один самодостаточный HTML без CDN и клиентских запросов, inline-SVG |

Все стадии идемпотентны и складывают артефакты в `reports/`.

### 3.2 Узкие места

**Нагрузка почти не влияет на время.** Объединённая корреляция Спирмена между
дневным объёмом города и временем доставки — **ρ = −0.092**. По децилям объёма
среднее время меняется с 31.88 мин в первом дециле до 31.24 мин в десятом
(`reports/load_curve.csv`): разница 0.64 мин при росте объёма почти в 28 раз.

![Кривая нагрузки](figures/bottleneck_load_curve.png)

**Категория влияет сильнее канала.** Внутри каждого канала закуски идут
≈39.95–39.99 мин, пицца — ≈26.49–26.56 мин, то есть разрыв около **+13.4 мин
(+50%)**. Канал меняет время в пределах десятых долей минуты
(`reports/bottleneck_channels.csv`):

| Категория | mp | web | other |
|---|---:|---:|---:|
| пицца | 26.56 | 26.55 | 26.49 |
| закуски | 39.97 | 39.99 | 39.95 |
| напитки | 30.00 | 29.85 | 30.05 |
| десерты | 24.98 | 24.97 | 25.05 |

![Время по каналу и категории](figures/bottleneck_channel_category_time.png)

**Рейтинг городов по деградации.** Индекс строится из наклона
`avg_time ~ qty` (секунд на 1000 заказов) и разбивает города на `worst10`,
`middle` (249 городов) и `best5`. Верхушка `worst10`
(`reports/bottleneck_cities.csv`):

| Ранг | Город | Индекс деградации | R² наклона |
|---:|---|---:|---:|
| 1 | Усолье-Сибирское | 2.02 | 0.0139 |
| 2 | Грозный | 1.63 | 0.0292 |
| 3 | Магадан | 1.18 | 0.0004 |
| 4 | Новый Уренгой | 1.08 | 0.0059 |
| 5 | Благовещенск | 1.02 | 0.0412 |

![Наклоны деградации по городам](figures/bottleneck_city_slopes.png)

Низкие R² — важная часть результата: рейтинг задаёт порядок проверки городов,
но сам по себе не доказывает устойчивый тренд роста времени в конкретном городе.

### 3.3 Гипотезы

| Гипотеза | Эффект | p-value | 95% CI | Вывод |
|---|---|---:|---|---|
| H1: доля `mp` растёт быстрее `web` | +5.70 п.п. | 2.07e-11 | [5.35; 6.03] | подтверждена |
| H2: выходные медленнее будней | −0.93% | 1.08e-41 | [−1.09; −0.76] | **отклонена: эффект значим в обратную сторону** |

H1: доля `mp` внутри пары `mp + web` растёт с 81.9% в январе до 87.6% в июне,
n = 30 / 31 день. Доля `web` падает на те же 5.7 п.п. по построению.

![Доли каналов](figures/hypothesis_channel_shares.png)

H2: медиана на city-day — 31.37 мин в выходные против 31.66 мин в будни,
n = 13 720 / 34 030. Интервал не содержит ноль, p = 1.08e-41, но знак
противоположен гипотезе: по выходным доставка быстрее на 0.29 мин. Правило
«значимый эффект в обратную сторону — это отклонение» зафиксировано в
`delivery/hypothesis.py` и покрыто тестом
`test_h2_rejects_significant_effect_in_wrong_direction`.

Числа H2 считаются по метрике, взвешенной по `qty`: `avg_time` — отношение
(время / заказы), и словарь данных запрещает усреднять его без веса. Прежняя
невзвешенная версия (`AVG(avg_time)` в `mart_city_daily`) давала p = 0.617 при
эффекте −0.02%; дефект закрыт, регресс-тест —
`tests/test_marts.py::test_city_time_is_qty_weighted_not_averaged`.

![Время в выходные и будни](figures/hypothesis_weekend_time.png)

### 3.4 SQL-слой

14 оконных запросов (`sql/windows.sql`): скользящее среднее, недельный рост,
накопительный итог, квартили дневного объёма, ранги городов по месяцам и по
времени доставки, Парето по городам, аномальные дни по правилу 3×MA7, разрывы
между заказами клиента. Самый тяжёлый — 30-дневный подсчёт активных клиентов,
196–221 мс в зависимости от прогона; из 14 запросов только он подходит к
границе 200 мс, остальные — до 31 мс (`reports/sql_timings.csv`).

Три пары «медленный / быстрый» вариант (`reports/sql_optimization.csv`):

| Пара | Строк | Медленный | Быстрый | Ускорение |
|---|---:|---:|---:|---:|
| running_order_count | 130 079 | 62–71 мс | 11–17 мс | **4–6×** |
| monthly_revenue_label | 6 | 8–16 мс | 2.6–5.4 мс | 3.0–3.2× |
| client_lifetime_revenue | 31 426 | 5.7–13.3 мс | 4.5–6.1 мс | 1.3–2.2× |

Диапазоны покрывают два прогона; точные значения последнего — в
`reports/sql_optimization.csv`. Лучшее ускорение — **4–6×** на накопленном
счётчике заказов по 130 079 строкам. Замеры сняты под `EXPLAIN ANALYZE` на
одной машине и одном датасете: wall-clock, один замер после прогрева. Между
прогонами разброс до ±30%, поэтому ускорения подаются как порядок величины,
а не точное число;
это сравнение вариантов запроса, а не бенчмарк СУБД.

## 4. Что НЕ подтвердилось

1. **Выходные не медленнее будней (H2).** p = 1.08e-41, эффект −0.93%,
   CI [−1.09; −0.76] — значимый эффект в обратную сторону. Гипотеза
   сформулирована до расчёта и отклонена по заранее заданному правилу;
   подгонять формулировку под данные не стали. → решение Р6.
2. **Модель машинного обучения не лучше сезонного бейзлайна.** HGB проигрывает
   `seasonal_naive` на всех трёх горизонтах (7.14 / 7.90 / 8.09% против
   5.40 / 6.01 / 6.25%). Рекомендация для h=7 и h=14 — именно бейзлайн. →
   решение Р1.
3. **Нагрузка не объясняет время доставки.** ρ = −0.092 и разница 0.64 мин
   между крайними децилями объёма: гипотеза «чем больше заказов, тем дольше
   доставка» на этих данных не работает — знак обратный. → решение Р2.
4. **Рейтинг городов статистически слабый.** У городов верхушки R² наклона
   0.0004–0.0412, поэтому индекс — приоритизация, а не доказанный тренд. →
   решение Р4.

## 5. Слой решений

Находка без решения — это отчётность. Ниже каждая находка из §3–§4 превращена
в решение: что делаем, с чего начинаем и при каком заранее заданном пороге
решение пересматривается. Порог задан до следующего прогона данных, чтобы
пересмотр не превращался в подгонку под новый взгляд на те же цифры.

### 5.1 Решения по находкам

| № | Находка | Решение | Первый шаг | Условие пересмотра |
|---|---|---|---|---|
| Р1 | Сезонный бейзлайн точнее ML: `seasonal_naive` 6.01 / 6.25% на h=7 / h=14 против 7.90 / 8.09% у HGB; Holt-Winters лучший только на h=1 (3.91%) | Планировать загрузку по `seasonal_naive` на 7 и 14 дней; ML-модель в прод не брать | Зафиксировать `seasonal_naive` как default планировщика; не тратить цикл на тюнинг HGB | Модель меняется, только если выигрывает у бейзлайна больше разброса по фолдам **и** разница подтверждена интервалом |
| Р2 | Объём не объясняет время: ρ = −0.092, децили 31.88 → 31.24 мин (0.64 мин при росте объёма в 28 раз), знак обратный гипотезе | Не масштабировать мощность доставки под пик объёма; объём не считать драйвером времени | Убрать сценарий «нагрузка → время» из операционных планов; оставить ρ как guardrail-метрику с пересчётом раз в месяц | ρ > +0.2 **или** положительный наклон на уровне заказа или часа |
| Р3 | Разрыв категорий +13.4 мин (+50%): закуски 39.95–39.99 против пиццы 26.49–26.56; канал меняет время в пределах десятых; разрыв постоянен, r(пицца, закуски) внутри города-дня = 0.002 | Не запускать операционную программу «ускорить закуски», пока не установлена природа разрыва; считать `avg_time` несравнимым между категориями | Запросить определение `avg_time` по категориям: что входит — приготовление, сборка, доставка; это дешевле любой оптимизации | Если определения совпадают — разрыв становится операционной гипотезой и требует замера на уровне заказа, а не агрегата |
| Р4 | Рейтинг городов слабый: индекс top-10 2.02…0.86, R² наклона 0.0004–0.0412, у четырёх из пяти < 0.03 | Рейтинг — очередь ручной проверки, не факт; никаких решений по одному городу без повторного замера | Проверить 3 города из top-10 на устойчивость: по аудиту сплит-половинная корреляция наклона почти нулевая (`docs/audit-2026-10-28.md`, п. 13) — рейтинг нестабилен; если не держится, понизить до диагностики | split-half ρ > 0.5 **и** R² > 0.1 на тех же городах |
| Р5 | Доля `mp` в паре `mp + web` выросла с 81.9 до 87.6% (+5.70 п.п., p = 2.07e-11, CI [5.35; 6.03]) | Отвечать коммерчески (ассортимент, промо, mp-операции), не операционно: время по каналам не различается | Ежемесячный мониторинг доли с порогом 2 п.п.; переименовать H1 в «доля `mp` в паре выросла» — текущая формулировка тавтологична | Разворот тренда два месяца подряд |
| Р6 | H2 отклонена: выходные быстрее на 0.29 мин (−0.93%), p = 1.08e-41 по наивному бутстрепу, CI [−1.09; −0.76]; кластеризация расширяет интервал и поднимает p на порядки | Принять отрицательный результат; не закладывать субботний буфер в SLA | Зафиксировать вердикт в `docs/preregistration.md` (правило + дата); не переформулировать H2 | Только новые данные уровня заказа; на этих данных вопрос закрыт |
| Р7 | SQL: running count 4–6×, ярлык выручки 3.0–3.2×, срок жизни клиента 1.3–2.2× (в шуме) | Внедрить только первую пару (running count); вторую и третью оставить как учебные примеры | Перенести rewrite в слой витрин/ETL; зафиксировать протокол замера: 3 прогрева, медиана, одна машина | Если lifetime-пара даёт устойчивое > 2× на трёх прогонах подряд |
| Р8 | Данные агрегированы: нет времени по заказу, курьеру, ресторану; сэмпл — 2 анонимных города; `cost` без валюты; 4 фолда; Superset не проверен | Единственный блокирующий шаг для роста глубины — заказ-уровневые данные с таймстампами; до них выводы остаются ассоциативными | Спецификация запроса: `order_id`, город, канал, категория, created / accepted / ready / picked / delivered, курьер, ресторан, 8–12 недель | После получения — повторить Р2 и Р3 на уровне заказа и часа, а не агрегата |
| Р9 | Superset-рецепт написан, но ни разу не запускался: Docker не поднимался, подключение не подтверждено | Не считать Superset проверенным артефактом: либо подтвердить запуском, либо оставить рецептом | Один прогон `superset/docker-compose.yml` + `init_superset.sh` и сохранённый лог/скриншот подключения; если Docker недоступен — пометить в README как непроверенное | Появился подтверждённый запуск — снять пометку; иначе рецепт остаётся вне раздела «что показывает» |

### 5.2 Решения-отказы

Отказ — тоже решение, и он дешевле действия. Ниже то, что мы решили **не**
делать по итогам анализа:

- не масштабировать мощность доставки под пик объёма (Р2);
- не внедрять ML-модель прогноза (Р1);
- не запускать программу ускорения закусок до подтверждения определения метрики (Р3);
- не публиковать рейтинг городов как установленный факт (Р4);
- не закладывать выходной буфер в SLA (Р6);
- не выдавать 1.3–2.2× за ускорение (Р7);
- не называть `cost` выручкой и не выводить из него рубли (Р8);
- не подавать Superset как работающий артефакт, пока нет подтверждённого запуска (Р9).

### 5.3 Как принимаются и пересматриваются решения

1. **Сначала дешёвая проверка, потом дорогая.** Определение `avg_time` (Р3) и
   устойчивость рейтинга (Р4) стоят часы; заказ-уровневые данные (Р8) — недели.
   Пока дешёвая проверка не сделана, дорогая не начинается.
2. **Порог пересмотра фиксируется заранее** — в таблице §5.1, а не после
   следующего прогона. Новый взгляд на те же данные не является основанием
   менять решение.
3. **Решение по агрегату помечается как ассоциативное.** Р2, Р3 и Р4 не
   утверждают причинность; их формулировки это фиксируют.
4. **Отказ, у которого есть измеримый порог, держится до него, а не до нового
   мнения.** Р2 и Р4 пересматриваются по порогам из таблицы; отказы без порога
   (Р8, Р9) снимаются только новым подтверждённым фактом.

Слой решений меняет приоритет работы: самый дешёвый следующий шаг — не новый
код и не новая модель, а два уточнения (определение `avg_time` в Р3 и
устойчивость рейтинга в Р4). Они стоят часы и могут отменить часть выводов.
Заказ-уровневые данные (Р8) — следующий по цене шаг, и он открывает проверку
Р2 и Р3 на той гранулярности, где вопрос вообще имеет смысл.

## 6. Ограничения данных

- **Агрегированная гранулярность.** Данные уже свёрнуты до
  день × город × канал × категория: нет времени по отдельному заказу, курьера,
  ресторана. Декомпозиция времени останавливается на уровне категории.
- **Сэмпл заказов — 2 анонимных города.** Он годится для SQL-слоя, но не для
  выводов по городам.
- **`cost` без подтверждённой валюты**, `avg_price` не согласуется с `cost` и
  не используется; выручку в рублях из этих данных вывести нельзя.
- **Четыре фолда бэктеста.** WAPE оценён на 28-дневном тестовом окне с четырьмя
  переобучениями: сравнение моделей на сотых долях процента здесь не значимо.
- **Причинности нет.** H1 и H2 — ассоциативные тесты на наблюдаемых агрегатах,
  эффект воздействия они не идентифицируют.
- **Superset не запускался** (нет Docker в среде сборки).

## 7. Как воспроизвести

```bash
uv sync --all-groups
uv run python -m delivery.etl
uv run python -m delivery.marts
uv run python -m delivery.forecast
uv run python -m delivery.bottlenecks
uv run python -m delivery.hypothesis
uv run python -m delivery.sql_layer
uv run python -m delivery.dashboard
uv run pytest        # 95 тестов
```

`delivery.etl` ожидает исходные CSV по пути `RAW_SOURCE` из
`delivery/config.py`; если файлы уже лежат в `data/raw/`, остальные стадии
работают без него.

Все числа в отчёте сверены с CSV в `reports/`:

| Таблица | Файл |
|---|---|
| WAPE по моделям и горизонтам | `reports/forecast_metrics.csv` |
| Время и позиции по каналу × категории | `reports/bottleneck_channels.csv` |
| Рейтинг городов | `reports/bottleneck_cities.csv` |
| Кривая нагрузки по децилям | `reports/load_curve.csv` |
| Гипотезы | `reports/hypothesis_results.csv` |
| Время оконных запросов | `reports/sql_timings.csv` |
| Пары оптимизаций | `reports/sql_optimization.csv` |
