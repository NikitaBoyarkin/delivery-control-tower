# A/B Test Results: delivery-control-tower (H1, H2)

**Гипотеза H1**: доля канала `mp` внутри пары `mp + web` растёт (январь → июнь 2022).
**Гипотеза H2**: время доставки в выходные выше, чем в будни.
**Длительность**: 2022-01-01 … 2022-06-30 (181 день) | **Данные**: 550 710 строк `day × city × channel × category`, 264 города.

> **Оговорка о дизайне.** Рандомизированного эксперимента в проекте нет: нет `user_id`,
> нет назначения варианта, нет экспериментальной метрики. H1 и H2 — наблюдательные
> двухгрупповые сравнения. Ниже они разобраны по протоколу A/B-ридаута (SRM, баланс групп,
> эффект с кластер-робастным интервалом, мощность), но причинного вывода не дают.

## 3. Рекомендация

**H1 — подтверждена, формулировку надо переписать.** Рост доли `mp` на 5.79 п.п. устойчив к
кластеризации по дням. Но «`mp` растёт быстрее, чем `web`» — тавтология: доля внутри пары
`mp + web` замкнута, рост `mp` механически означает падение `web`. Корректная формулировка:
«доля `mp` в паре `mp + web` выросла с 81.8% до 87.6% за январь → июнь». Причинность не
установлена: между январем и июнем могли измениться что угодно ещё.

**H2 — гипотеза отклонена, но не так, как считает проект.** В исходной постановке («выходные
медленнее») разница не подтверждена — потому что направление **обратное**: выходные доставки
идут быстрее на ≈0.29 мин (−0.93%, CI [−0.34; −0.25]). Нулевой результат в `hypothesis_results.csv`
(p = 0.617, эффект −0.02%) — артефакт метрики, а не отсутствие эффекта.

**Дефект (исправлен).** `delivery/marts.py` строил `AVG(s.avg_time)` — среднее по ячейкам
без веса — в `mart_city_daily` и в `dim_city.avg_delivery_time`. `avg_time` — это отношение
(сумма времени / заказы), и словарь проекта прямо запрещает такое усреднение:
`docs/data_dictionary.md:14,18` — «при агрегации за период нельзя брать `AVG(...)`, только
повторное взвешивание по `qty`». Невзвешенное среднее даёт ячейке с 3 заказами тот же вес,
что ячейке с 300, и это съедает эффект.

Стало: `SUM(avg_time * qty) / SUM(qty)` в обоих местах. Сборка мартов, `bottlenecks`,
`hypothesis` и `dashboard` перезапущены; `hypothesis_results.csv` теперь даёт H2
−0.93%, p = 1.08e-41.

Заодно закрыт второй дефект: `_supported` в `delivery/hypothesis.py` считал гипотезу
подтверждённой при любом значимом эффекте, включая обратный по знаку. Теперь требуется
совпадение с предзарегистрированным направлением; иначе нота помечается «эффект значим
в обратную сторону».

Регресс-тесты: `test_city_time_is_qty_weighted_not_averaged` (mutation control: на
невзвешенной сборке расходятся 47 746 из 47 750 city-day) и
`test_h2_rejects_significant_effect_in_wrong_direction`.

## 4. Ожидаемый эффект

Арифметика, не прогноз: 0.293 мин × 33 167 293 заказа периода ≈ 9.7 млн минут разницы
«выходные против будней» на горизонте полугодия. Интерпретировать как «столько сэкономим»
нельзя — это наблюдательное сравнение, а не эффект вмешательства.

## 5. Что нужно, чтобы это стало A/B-тестом

| Сейчас есть | Нужно |
|---|---|
| Агрегаты день × город × канал × категория | `user_id` / `order_id` с назначением варианта |
| Две группы, заданные календарём | Плановое соотношение сплита и лог назначения |
| Наблюдаемая метрика `avg_time` | Та же метрика + guardrails (доля отмен, SLA-нарушения) на пользователя |
| Нет даты запуска варианта | Дата старта, дата первого анализа, исключение периода раскатки |

## Воспроизведение

```bash
uv run python scripts/ab_test_analyzer.py --readout all
uv run python scripts/ab_test_analyzer.py --check-srm --n-control 34030 --n-test 13720 --expected-share 0.28729
```

Выход: `reports/ab_test_metrics.csv`.

| Артефакт | Роль |
|---|---|
| `scripts/ab_test_analyzer.py` | SRM, мощность/MDE, Welch, two-proportion z, кластерный бутстреп, баланс групп |
| `reports/ab_test_metrics.csv` | Все спецификации с интервалами и p-value |

`mart_city_daily` на него не влияет.
